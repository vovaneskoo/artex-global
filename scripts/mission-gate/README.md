# Управление миссией ARTEX

`mission-up.sh <IPv4>...`, `mission-down.sh`, `mission-status.sh` управляют сетевым
жизненным циклом. Набор инструментов, scope движка и бюджеты не меняются.

Состояние хранится в `~/projects/artex-bench/artifacts/mission-gate/state.json`:
`inactive`, `starting`, `active`, `stopping`, `cleanup-failed`, уникальный ID,
список целей, последняя ошибка и сохранённое состояние VPN до запуска. Замена атомарна с fsync; up/down сериализованы
fcntl-lock. status только читает. `ARTEX_MISSION_STATE_DIR` задаёт другой каталог.
Для тестов/другой установки доступны `ARTEX_MULLVAD`, `ARTEX_LIMACTL`, `ARTEX_MISSION_VM`.

## Запуск

1. Проверить `mission-status.sh`: active или незавершённая очистка требуют down.
2. `mission-up.sh <IPv4>...`: прочитать стабильное состояние VPN/lockdown и сохранить
   его вместе с намерениями до сетевых изменений; включить VPN, проверить выход,
   включить lockdown, добавить и проверить помеченные правила целей, затем active.
3. Работать через существующий интерфейс ARTEX.
4. `mission-down.sh`: сначала отозвать доступ в inode журнала, затем записать stopping и закрыть цели,
   удаление принадлежащих миссии ACCEPT, проверка отсутствия, выключение VPN.

Реле открывает соединения только при active; удаление/повреждение state.json
закрывает доступ. Отзыв закрывает существующие соединения с опросом каждые 100 мс. Каждый handler держит shared flock до закрытия сокетов; down ждёт exclusive flock перед освобождением VPN. Если leases не ушли за 5 секунд, очистка завершается ошибкой с сохранением lockdown.
Старый ID не оживает при следующей миссии. Оба entry point используют реализацию
`scripts/isolated-run/relay.py`; bench-файл — только wrapper. Relay CLI сохраняется:
`relay.py [host] [port] [upstream] [logfile]`.

На down перед ESTABLISHED устанавливаются точечные DROP 80/443 для целей миссии:
одного удаления ACCEPT недостаточно для уже установленных соединений.
Эти помеченные запреты сохраняются после down; up снимает их только для вновь
выбранных целей после включения VPN. Запреты не затрагивают другие адреса/порты.

## Ошибки и восстановление

Перед записью stopping контроллер снимает owner-write bit существующего state.json
и делает fsync. Поэтому отказ выделения временного файла, записи или os.replace
не оставляет старый active grant. JSON и mode читаются из одного открытого inode.
Режим 0400 означает отзыв; 0500 дополнительно сохраняет намерение отката запуска,
если даже следующий JSON не удалось записать. status показывает такой журнал как
cleanup-failed, сохраняя цели. Эти mode bits — внутренние флаги обычного JSON-файла.
Не менять mode вручную и не восстанавливать active из резервной копии: повторить down
после устранения ошибки. Обычная атомарная запись устанавливает новый inode 0600;
тот же отозванный ID нельзя записать обратно как active через state writer.

Если изменение inode metadata недоступно, контроллер пытается записать cleanup-failed
атомарно. Если недоступны оба способа и отзыв не подтверждён, он явно сообщает
RELAY REVOCATION UNCONFIRMED и сохраняет VPN-защиту. При полном отказе хранилища
сначала остановить relay, затем восстановить доступ к журналу и повторить down;
такой отказ нельзя считать успешным закрытием доступа.

Откат неудачного up отличается от обычного down: только после подтверждённой
очистки правил он восстанавливает сохранённые connected/disconnected и lockdown
on/off. Tunnel state проверяется до снижения lockdown; команды восстановления
ожидают connect/disconnect и результат проверяется повторно. Намерение restore
сохраняется для повторного down после прерывания/ошибки. Если снимок VPN не удалось
прочитать, up возвращает ошибку до изменения VPN. Обычный down успешно поднятой
миссии по-прежнему выключает lockdown и VPN. Старые v1 starting/stopping/
cleanup-failed и импортированные legacy targets без снимка очищаются с сохранением
текущего VPN; прежнее состояние не угадывается. Active v1 сохраняет обычный down.

Успешный `iptables -S OUTPUT` отличает отсутствие правила от ошибки связи,
sudo или файрвола. При неопределённости down возвращает ненулевой код,
сохраняет цели и cleanup-failed, оставляет LLM закрытым и lockdown включённым.
После восстановления VM/прав повторить down. Не выключать VPN вручную, пока
очистка не подтверждена. Если выключение VPN само завершилось ошибкой, контроллер
пытается вернуть lockdown и фиксирует ошибку восстановления, если она произошла.
При SIGKILL/потере питания starting/stopping не выдаёт grant; выполнить down.

Если state.json повреждён, автоматическая очистка и запуск запрещены: восстановить
журнал из резервной копии с НЕактивным состоянием после сверки файрвола. Не ставить
active вручную. Старые armed/strict никогда не grant. targets.txt импортируется
только для очистки и сохраняется как исходный журнал. Старый armed без targets
требует ручной сверки файрвола; автоматическое выключение защиты невозможно.

## Обновление/откат

Перед заменой проверить отсутствие выполняющейся миссии/задач и сохранить файлы,
конфигурацию и старый журнал. Перезапустить уже работающий relay: замена файла
не обновляет процесс. Первый запуск без состояния закрыт. Для отката сохранить
VPN-защиту и выполнить down; восстановление старых скриптов НЕ должно возвращать
armed/active. Повреждённые/неопределённые состояния требуют сверки, а не сброса.

Проверки: `python3 -m unittest discover -s tests -p test_mission_gate.py -v`.
Они используют подставные команды VPN/VM и локальный upstream без внешних запросов.
Реле и гостевой файрвол не являются защитой от root внутри VM; DNS и доступ гостя
к хосту сохраняют ранее описанные ограничения. Запись canary отражает соединения
через реле, а не доказывает отсутствие всех других видов трафика.
